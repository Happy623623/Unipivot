# 배포 절차 — api는 Cloud Run, web은 Vercel

> 📝 기준: PRD v0.9 9장(기술 스택·스케줄러)·14장 · README "데모" 절 · `docs/데모_리허설.md`
>
> 처음에는 1~6장을 차례로 하고, 그 뒤 코드를 다시 올릴 때는 7장만 한다. PowerShell에 붙이는 명령에는 한글을 넣지 않았다
> (`YOUR-PROJECT`처럼 영어 자리표시만 있다).

## 0. 한눈에

| | api | web |
| --- | --- | --- |
| 어디 | Google Cloud Run, 서울(`asia-northeast3`), 서비스 이름 `unipivot-api` | Vercel Hobby, 함수 지역 서울(`icn1`, `web/vercel.json`) |
| 올리는 법 | api 폴더에서 `uv run python -m app.deploy.cloudrun deploy …`(빌드는 Cloud Build가 한다 — PC에 Docker가 없어도 된다) | GitHub `main`에 합치면 Vercel이 빌드한다 |
| 비밀값 | Secret Manager. 명령이 `api/.env`에서 옮기고 화면에는 이름과 길이만 찍는다 | 없다(`NEXT_PUBLIC_…`은 브라우저에 그대로 보이는 값이다) |
| 고정한 것 | 인스턴스 **최대 1개**, **CPU 늘 켬**, 1 vCPU · 메모리 1GiB, 요청 300초 | Root Directory `web`, Production 주소만 쓴다 |
| 지금 주소(10/25 첫 배포) | `https://unipivot-api-p6gcp4fbka-du.a.run.app` | `https://unipivot.vercel.app` |

왜 이렇게 했나:

- **최대 1개**: 정기 작업은 서버 안 스케줄러가 돌린다(`app/scheduler.py`). 인스턴스가 둘이면 같은 일이 두 번 돈다.
  평소에는 1개지만, 새 버전을 올리는 동안은 새 인스턴스가 먼저 뜨고 옛 인스턴스가 꺼지기까지 잠깐 2개가 겹친다(최대 개수는 버전 단위다).
  그 사이 두 인스턴스가 같은 알림을 골라도 알림 행을 먼저 닫아 확정한 쪽만 푸시를 보낸다(10/25). 옛 인스턴스가 푸시 도중 꺼지면 그 푸시 한 번은
  빠질 수 있다(두 번 보내느니 빠뜨린다 — 명세 10장. 알림함에는 남는다). 공고 알림 예약도 중복돼도 안전하다.
- **CPU 늘 켬**(인스턴스 기준 과금): 준비하기·포스터 추출·강의자료 요약은 202로 답한 뒤 같은 서버에서 계속 돈다(`app/background.py`).
  Cloud Run 기본값(요청이 없으면 CPU를 끊는다)에서는 이 일들이 멈춘다. 1 vCPU 아래로는 이 방식을 쓸 수 없다.
- **서울**: Supabase(ap-northeast-2)·Vercel 함수(icn1)와 같은 도시다. LearningX·온통청년에도 국내 지역에서 붙는다.
- **Gemini는 서비스 계정 권한**으로 부른다(키 파일 없음). 로컬과 같은 `GOOGLE_CLOUD_PROJECT`에 배포한다.

## 1. 준비 (한 번)

- **Google Cloud CLI**를 설치하고(설치 뒤 PowerShell을 새로 연다) 로그인한다. 로컬 Gemini용 `application-default login`과는 다른 로그인이다.

  ```powershell
  gcloud auth login
  gcloud config set project YOUR-PROJECT-ID
  ```

  뒤의 `gcloud` 명령(6·7·8장)은 이 설정 프로젝트를 쓴다. `YOUR-PROJECT-ID`는 `api/.env`의 `GOOGLE_CLOUD_PROJECT`와 같은 값이다.
  자리표시를 글자 그대로 넣으면 `must be set to a valid project ID`로 거절된다(설정은 바뀌지 않는다).
  `active project does not match the quota project` 경고가 뜨면 로컬 Gemini 로그인의 과금 프로젝트도 맞춘다:
  `gcloud auth application-default set-quota-project YOUR-PROJECT-ID`.

- **`api/.env`를 확인한다**. 배포 서버는 이 파일과 같은 값에서 출발한다(명령이 읽어서 옮긴다).
  - `DATABASE_URL` — Supabase 대시보드 **Connect > Session pooler** 주소(`…pooler.supabase.com:5432`)여야 한다.
    직접 연결(`db.<ref>.supabase.co`)은 IPv6 주소라 Cloud Run에서 닿지 않는다(명령이 막는다).
  - `GOOGLE_CLOUD_PROJECT` — Gemini를 부르는 프로젝트. 배포도 이 프로젝트에 한다.
  - `TOKEN_ENCRYPTION_KEY` — **로컬에서 쓰던 키 그대로**. 바꾸면 저장된 Google·LMS 토큰을 못 읽는다.
  - 나머지(`SUPABASE_SECRET_KEY`·`GOOGLE_OAUTH_CLIENT_ID/SECRET`·`VAPID_*`·`YOUTH_API_KEY`·`INTERNAL_API_KEY`)는 없으면 명령이 무엇이
    빠지는지 알려 준다. 시험용으로만 바꾸는 주소(`LMS_API_BASE`·`SUPABASE_STORAGE_BASE`·`GOOGLE_*_URL` 등)는 넘기지 않는다 — 배포 서버는
    진짜 주소(기본값)를 쓴다.
- **크레딧**: Cloud Run·Cloud Build·Secret Manager도 Gemini와 같은 무료 체험 크레딧에서 빠진다(8장 비용).

## 2. GCP 설정 (한 번)

api 폴더에서 먼저 미리 보고(아무것도 바꾸지 않는다), 그다음 돌린다.

```powershell
cd api
uv run python -m app.deploy.cloudrun setup --dry-run
uv run python -m app.deploy.cloudrun setup
```

하는 일: API 여섯 개 켜기(Cloud Run·Cloud Build·Artifact Registry·Secret Manager·Gemini·Compute Engine), 서버용 서비스 계정
`unipivot-api@…`을 만들고 `roles/aiplatform.user`(Gemini)·`roles/secretmanager.secretAccessor`(비밀값 읽기) 주기, 소스 빌드 계정
(`{프로젝트 번호}-compute@…`)에 `roles/run.builder` 주기. 다시 돌려도 된다. 권한이 퍼지는 데 1~2분 걸린다.

## 3. web을 Vercel에 (주소를 먼저 정한다)

> **web의 Next.js가 16.4.3 이상인지 먼저 본다**(`web/package-lock.json`의 `node_modules/next`). 16.4.0에는 critical 보안 권고가 있었고 10/24에 16.4.3으로 올렸다.

1. vercel.com → **Add New → Project** → GitHub의 `Unipivot` 저장소 **Import**(옛 `Unipivot-old`가 아니다). 목록에 없으면
   "Adjust GitHub App Permissions"에서 Vercel 앱이 이 저장소를 보게 한다. **Project Name**이 주소가 된다(`unipivot` → `https://unipivot.vercel.app`).
2. **Root Directory: `web`** (Framework는 Next.js로 저절로 잡힌다)
3. **Environment Variables**(Production): `web/.env.local`과 같은 값을 넣는다. API 주소는 4장 뒤에 넣는다.

   | 이름 | 값 |
   | --- | --- |
   | `NEXT_PUBLIC_USE_MOCKS` | `false` |
   | `NEXT_PUBLIC_SUPABASE_URL` | `web/.env.local`과 같다 |
   | `NEXT_PUBLIC_SUPABASE_ANON_KEY` | `web/.env.local`과 같다 |
   | `NEXT_PUBLIC_VAPID_PUBLIC_KEY` | `web/.env.local`과 같다(서버의 `VAPID_PRIVATE_KEY`와 짝) |
   | `NEXT_PUBLIC_API_BASE_URL` | 4장 끝에 찍히는 값 |

   `NEXT_PUBLIC_…`은 빌드할 때 화면 코드에 박힌다. 바꾸면 **Deployments → 최신 → Redeploy**를 눌러야 반영된다.
   변수의 Type은 **Config**로 둔다. Secret을 고르면 "Remove the public framework prefix…"로 저장이 막힌다(`NEXT_PUBLIC_…`은 어차피
   브라우저에 보이는 값이다). 자물쇠(Sensitive)로 저장된 값도 빌드에는 들어간다.
4. **Deploy** → 주소 `https://YOUR-PROJECT.vercel.app`을 적어 둔다. 이 단계의 화면은 API 주소가 없어 오류 안내가 뜬다(정상).
5. 함수 지역이 서울(icn1)인지 본다. `web/vercel.json`이 정하고, 대시보드(Settings → Functions → Function Regions)보다 이 파일이 앞선다.
   PowerShell에서 `curl.exe -sI https://YOUR-PROJECT.vercel.app/auth/callback | Select-String "x-vercel-id|HTTP/"` →
   `X-Vercel-Id: icn1::icn1::…`(두 번째가 함수가 돈 곳)이면 맞다. Overview의 미리보기 그림이 하얀 것은 정상이다(로그인 화면으로 넘어가기 전을 찍는다).

미리보기 배포 주소(`…-git-….vercel.app`)는 CORS·Supabase 허용 목록에 넣지 않는다 — 거기서는 로그인이 안 된다. 데모는 Production 주소만 쓴다.

## 4. api를 Cloud Run에

```powershell
cd api
uv run python -m app.deploy.cloudrun deploy --web-origin https://YOUR-PROJECT.vercel.app --dry-run
uv run python -m app.deploy.cloudrun deploy --web-origin https://YOUR-PROJECT.vercel.app --min-instances 0
```

- `--dry-run`은 무엇을 올릴지(비밀값 이름·길이, 환경 변수 이름, 빠지는 기능)만 찍는다. 고칠 것이 있으면 배포하지 않고 목록을 찍는다.
  `알림:` 줄(빠지는 기능)은 배포를 막지 않는다. `INTERNAL_API_KEY`가 없다는 알림이 나오면 `api/.env`에 임의의 긴 값을 넣고(`api/.env.example`의
  만드는 명령) 다시 미리 본다 — 6장의 수동 확인과 배포 서버의 지표 조회에 쓴다.
- 처음은 5~10분 걸린다(Cloud Build가 `api/Dockerfile`로 이미지를 만든다). 끝에 **api 주소**와 **Vercel에 넣을 값**이 찍힌다.
- 그 값을 Vercel의 `NEXT_PUBLIC_API_BASE_URL`에 넣고 **Redeploy**한다.
- 배포한 뒤에는 **로컬 `api/.env`의 `SCHEDULER_ENABLED`를 `false`로** 둔다. 같은 DB에 정기 작업이 두 번 돈다(명령이 알려 준다).
- 무엇이 올라가는지는 `api/.gcloudignore`가 정한다(`.env`·`.venv`·`tests`는 안 올라간다). 명령은 이 파일과 `api/.dockerignore`에
  `.env` 줄이 없으면 멈춘다.

## 5. Supabase·Google 설정

- **Supabase → Authentication → URL Configuration**
  - **Site URL**: `https://YOUR-PROJECT.vercel.app`
  - **Redirect URLs**에 `https://YOUR-PROJECT.vercel.app/auth/callback**`을 **더한다**(`http://localhost:3000/auth/callback**`은 그대로 둔다).
    캘린더 연결은 콜백 뒤에 `?connect=calendar&next=…`가 붙어서 끝의 `**`가 있어야 맞는다.
- **Google OAuth 클라이언트는 바꿀 것이 없다.** Google이 돌아오는 곳은 Supabase 주소(`https://<ref>.supabase.co/auth/v1/callback`)다.
  게시 상태가 테스트면 데모 계정이 테스트 사용자에 있어야 한다. 프로덕션으로 게시하는 법은 아래 '앱 게시'다.

### 캘린더 권한 유지 (`GOOGLE_OAUTH_CLIENT_ID`·`GOOGLE_OAUTH_CLIENT_SECRET`)

4장 미리보기의 `GOOGLE_OAUTH_CLIENT_ID·SECRET이 없어요` 알림이 이것이다. 없으면 Google 캘린더 권한이 55분 뒤 끊겨 학생이 다시 연결해야 한다.
서버는 캘린더 접근 토큰을 갱신할 때 **Supabase 로그인에 쓰는 것과 같은 OAuth 클라이언트**의 ID·비밀값을 쓴다(다른 클라이언트면 Google이 갱신을 거절한다).

1. **Client ID**: Supabase → Authentication → Sign In / Providers → Google의 Client ID를 복사한다(쉼표로 여러 개가 있으면 웹 로그인에 쓰는 첫 번째 값).
2. **Client Secret**: 그 클라이언트를 만들 때 따로 적어 둔 값이 있으면 그것을 쓴다. 없으면 Google Cloud 콘솔 → **Google Auth Platform → Clients** →
   그 클라이언트 → **Add Secret**. 새 비밀값은 만든 그 화면에서만 전체가 보이고(나중에는 끝 4자리만), 한 클라이언트에 둘까지 둘 수 있으며 끄기 전까지 둘 다 쓰인다.
3. `api/.env`의 `GOOGLE_OAUTH_CLIENT_ID=`·`GOOGLE_OAUTH_CLIENT_SECRET=`에 넣는다(값은 채팅에 붙이지 않는다). 2에서 새로 만들었으면 Supabase의
   Google Provider 비밀값도 같은 새 값으로 바꾼다.
4. `main`을 pull한 상태에서 4장의 deploy를 `--dry-run`으로 먼저 돌려 그 알림이 사라졌는지 보고, `--min-instances` 없이 다시 돈다.
   deploy는 늘 지금 폴더의 코드로 이미지를 새로 빌드한다(다른 브랜치에 있으면 그 코드가 올라간다). 비밀값은 바뀐 것만 새 버전으로 올라간다.
5. 배포 주소에서 로그인 → 캘린더 연결 → 마감일 등록이 되면, 2에서 새로 만든 경우에만 옛 비밀값을 **Disable**한다(Supabase 값을 바꾸기 전에 끄면 로그인이 깨진다).

로컬 api도 같은 `api/.env`를 읽으므로 로컬 캘린더도 함께 55분 문제가 없어진다.

### 앱 게시 (프로덕션)

테스트 상태에서는 캘린더 권한이 7일 뒤 끊기고, 테스트 사용자로 넣은 계정만 쓸 수 있다. 게시하려면 홈페이지와 개인정보 처리방침 주소가
있어야 한다. 처리방침은 web의 `/privacy`다(로그인 없이 열리는 정적 페이지). 로그인 화면 아래와 앱 사이드바 아래에 링크가 있어서
홈페이지(`/`)의 HTML에도 처리방침 링크가 들어 있다.

1. 로그아웃한 창에서 `https://YOUR-PROJECT.vercel.app/privacy`가 열리는지 본다.
2. Google Cloud 콘솔 → **Google Auth Platform → 브랜딩**에 앱 홈페이지 `https://YOUR-PROJECT.vercel.app`과 개인정보처리방침
   `https://YOUR-PROJECT.vercel.app/privacy`를 넣는다. **승인된 도메인**을 요구하면 `YOUR-PROJECT.vercel.app`과 Supabase 콜백 주소의
   도메인(`<ref>.supabase.co`)을 넣는다.
3. **대상 → 앱 게시**를 누른다.
4. 배포 주소에서 로그아웃하고 다시 로그인한다. 로그인은 기본 범위만 받아 그대로다. 캘린더를 연결하면 "Google에서 확인하지 않은 앱"
   화면이 뜬다(고급 → 이동). 확인(검증)을 받기 전에는 캘린더 권한을 받는 새 사용자가 100명까지다.

## 6. 확인

PowerShell(지금 주소다. 서비스를 새로 만들면 4장 끝에 찍힌 주소로 바꾼다):

```powershell
$api = "https://unipivot-api-p6gcp4fbka-du.a.run.app"
Invoke-RestMethod "$api/health"
gcloud run services logs read unipivot-api --region asia-northeast3 --limit 30
```

예상: `Invoke-RestMethod`는 `status` 아래에 `ok`를 찍는다. 로그(새것부터)에 `스케줄러를 켰어요: 알림 발송, LMS 동기화, 공고 알림 예약`(온통청년 키가 있으면 청년정책 수집도)이 있다.
최소 0이면 인스턴스가 꺼져 있다가 첫 요청에 켜져서, 로그는 `/health`를 연 뒤에 보인다.

브라우저(Vercel 주소):

1. Google로 시작하기 → 홈 피드 → 공고 상세가 열린다. 개발자 도구 콘솔에 CORS 오류가 없다.
2. 포스터 한 장을 올려 확인 화면까지 간다 — Gemini 권한 확인(로그에 `PERMISSION_DENIED`가 있으면 2장을 다시).
3. 학업 → LearningX 동기화를 한 번 — 학교 서버가 클라우드 주소를 막지 않는지 확인.
4. 설정 → 알림 → "이 브라우저에서 알림 받기".

정기 작업을 손으로 한 번 불러 보려면(선택. 키는 창에만 입력하고 채팅에 붙이지 않는다. 첫 청년정책 수집은 1~3분 걸려서 `-TimeoutSec 300`을 붙였다):

```powershell
$secure = Read-Host "INTERNAL_API_KEY" -AsSecureString
$key = [Runtime.InteropServices.Marshal]::PtrToStringBSTR([Runtime.InteropServices.Marshal]::SecureStringToBSTR($secure))
Invoke-RestMethod -Method Post -TimeoutSec 300 -Headers @{ "X-Internal-Key" = $key } "$api/api/v1/internal/jobs/fetch-policies"
Invoke-RestMethod -Method Post -TimeoutSec 300 -Headers @{ "X-Internal-Key" = $key } "$api/api/v1/internal/jobs/lms-sync"
Remove-Variable key, secure
```

## 7. 다시 올리기·되돌리기

- **코드를 다시 올릴 때**: `main`을 pull한 상태에서 4장의 deploy 명령을 다시 돈다. `--min-instances`를 빼면 지금 값을 그대로 둔다
  (데모 기간에 다시 올려도 꺼지지 않는다). 비밀값은 바뀐 것만 새 버전으로 올라간다.
- **비밀값을 바꿀 때**: `api/.env`를 고치고 deploy를 다시 돈다.
- **되돌리기**: Cloud Run 콘솔 → `unipivot-api` → 버전(Revisions)에서 이전 버전에 트래픽 100%. 명령으로는:

  ```powershell
  gcloud run revisions list --service unipivot-api --region asia-northeast3
  gcloud run services update-traffic unipivot-api --region asia-northeast3 --to-revisions REVISION_NAME=100
  ```

  주의:
  - 이렇게 고정하면 서비스가 "최신 버전을 따라가기"를 멈춘다. **고친 코드를 다시 올린(deploy) 뒤에는 꼭**
    `gcloud run services update-traffic unipivot-api --region asia-northeast3 --to-latest`를 돌린다.
    안 하면 deploy가 성공과 주소를 찍어도 새 버전은 트래픽 0%라 옛 코드가 계속 답한다.
  - 되돌려도 **비밀값은 돌아가지 않는다**(항상 최신 버전을 읽는다). 옛 버전은 자기 시절의 최소 인스턴스 값도 그대로 가진다.

## 8. 평소와 데모 기간 (비용)

| | 최소 인스턴스 | 비용 | 정기 작업 |
| --- | --- | --- | --- |
| 평소 | 0 | 쓰는 동안(+쉬는 몇 분)만 | 서버가 꺼져 있는 동안 안 돈다(알림 발송은 켜질 때 바로 한 번). 첫 요청이 몇 초 늦다 |
| 데모 기간(D-7 ~ 끝난 날) | 1 | 1 vCPU·1GiB를 늘 켬. 기본 단가(Tier 1)로 한 달 약 $52(CPU 약 $47 + 메모리 약 $5), 서울은 Tier 2라 더 비싸다(대략 $72로 추정 — 가격 계산기로 확인) | 제때 돈다 |

```powershell
gcloud run services update unipivot-api --region asia-northeast3 --min-instances 1
gcloud run services update unipivot-api --region asia-northeast3 --min-instances 0
```

`gcloud config get-value project`가 배포한 프로젝트가 아니면(1장) 두 명령 끝에 `--project YOUR-PROJECT-ID`를 붙인다. 무료 체험 크레딧이 다 되면
과금 계정을 올리기 전까지 서비스가 멈춘다(크레딧 만료일은 `docs/LLM_모델_선정.md`).

## 9. 막히면

| 보이는 것 | 이유 | 할 일 |
| --- | --- | --- |
| deploy가 빌드에서 `PERMISSION_DENIED` | 2장을 안 했거나 권한이 아직 퍼지는 중 | 2장을 다시 돌리고 2분 뒤 다시 |
| 로그에 Gemini `403 PERMISSION_DENIED` | 서비스 계정에 `roles/aiplatform.user`가 없다 | 2장 |
| 화면의 모든 요청이 CORS 오류 | `--web-origin`이 실제 주소와 다르다(미리보기 주소 등) | 맞는 주소로 4장을 다시 |
| 로그인 뒤 `localhost:3000/?code=…`(연결 거부)나 엉뚱한 곳으로 간다 | Supabase Redirect URLs에 배포 주소가 없어 Site URL(처음 값은 localhost)로 보냈다 | 5장의 Site URL·Redirect URLs. 그 탭은 닫고 배포 주소에서 다시 로그인한다 |
| `/health`는 되는데 로그인한 요청이 503 | 로그인·DB 설정 | 시작할 때 찍힌 로그의 "설정 확인" 줄을 본다 |
| 다시 올렸는데 화면이 안 바뀐다 | 되돌리기(7장)로 트래픽을 옛 버전에 고정해 둔 채다 | `gcloud run services update-traffic unipivot-api --region asia-northeast3 --to-latest` |
| 로그에 `MaxClientsInSessionMode` | Supabase 세션 풀러의 연결 수 한도(무료는 보통 15)를 로컬 api·배포 서버·CLI가 합쳐 넘었다 | 쓰지 않는 로컬 api·CLI를 끈다. 계속되면 `DATABASE_URL`을 트랜잭션 풀러(포트 6543)로 바꿔 deploy를 다시(코드는 이미 대응한다) |
| 정기 작업 결과가 없다 | 최소 0이라 서버가 꺼져 있었다 | 데모 기간에는 최소 1(8장) |
| LearningX 동기화만 실패 | 학교 서버가 클라우드 주소를 막았을 수 있다 | 로그의 상태 코드를 보고, 안 되면 데모 노트북의 로컬 api로 보여 준다 |
| Vercel 환경 변수 저장이 "Remove the public framework prefix…"로 막힌다 | `NEXT_PUBLIC_…`을 Secret 종류로 넣었다 | Type을 Config로(3장) |
| 캘린더 연결이 한 시간쯤 뒤 다시 연결하라고 한다 | 서버에 `GOOGLE_OAUTH_CLIENT_ID`·`SECRET`이 없다 | 5장 "캘린더 권한 유지" |
| gcloud가 `active project does not match the quota project` 경고 | 로컬 Gemini 로그인의 과금 프로젝트가 다르다 | 1장의 `set-quota-project` |
